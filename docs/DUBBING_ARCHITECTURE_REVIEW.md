# VideoRoll 配音架构与泛化审查（2026-10-14）

## 当前结论

近期针对特定 S100 视频做过快迭代，把“测试视频能跑通”误当作模型质量提升，确实出现过拟合的工程风险。最明显的两个问题：

1. `speech_units._join` 曾以字符串相同前缀自动删除上一段内容。即使只是讲者有意重读，也会丢失文字。**已完全撤销自动删词**，不允许通过提高前缀匹配阈值掩盖风险。
2. `auto_group_speech` 曾默认启用，使用 2.3s/0.35s/15s 等单次调参启发式直接影响所有任务。**默认已关闭**；只有用户主动开启实验性功能，才合并短字幕。现有逐句配音主流程仍保留。

## 横向对照（与源码/项目文档一致）

- [pyVideoTrans 架构](https://github.com/jianchang512/pyvideotrans/blob/main/docs/architecture.md)：明确独立的识别、说话人、翻译、逐句 TTS、音画对齐 (`_rate.py`)、二次 ASR、最终混音阶段。VAD 阶段可合并短语，配音并不默认拼接所有短字幕。对齐可选择音频加速、视频慢速、静音间隙回收、二次识别，而不是一条固定 2× 规则。
- [VideoLingo 官方架构简介](https://github.com/Huanshere/VideoLingo/blob/main/docs/pages/docs/introduction.en-US.md)：词级 ASR/forced alignment、语义分句、术语词典、翻译—反思—适配、合成与配音对齐相互独立；公开说明多人说话分离和自然度仍有局限。

## 不能再用来宣称质量提升的指标

- “字幕 278 条被合成 206 段”只是工作单元减少，无法保证丢失词率、内容保真、自然度或对齐质量。
- “首段 WAV 非静音 / HTTP 200 / 音频结束时间合法”只证明系统可工作，不证明中文朗读自然。
- “调试 2× 倍速成功”不代表成片质量合格；倍速上限不是中文口播优化算法。
- 只针对出错句子的正向断言不能证明算法泛化；必须包含反例、不同话题、中英混合和数据保真性质测试。

## 长期建议（在独立评审批准后逐阶段推进）

1. 首先建立小型评测集：科技讲解、访谈、多说话人、连续课程、快语速/噪声样本；记录每条语义、原文时间戳及授权音色。
2. 建立独立、带版本的“口播稿”产物，保存原 ASR、译文、可编辑口播稿以及句子与原词的映射。任何内容缩写或去重必须可审查且默认不覆盖原文。
3. 选择具备说话人依据和静音信息的自然分段，依据发音估算时长，但不根据单条翻译字幕短行直接决定 TTS 输入。
4. TTS 输出后做实际长度测量、必要的二次识别/对齐，再分配静音间隙、适量音频伸缩及必要的视频调整。语速异常暴露为指标，而不是不断扩展倍速阈值。
5. 实现质量门槛（字符/词语遗漏率、字幕交叉率、声音稳定性、少量 A/B 听感复核）。只有经过多视频对照才能把实验开关改为默认。

## 变更原则

- 最小补丁优先：只修正有真实证据的缺陷，不在每次测试失败后新增专用条件。
- 保持 VideoRoll 原有字幕、翻译、渲染和发布主链路稳定；配音对其采用独立的输入、产物和任务状态。
- 生产部署前至少执行相关回归与前端构建；运行中配音任务未经用户指示不得自动重试/重新生成。
